# Incident: 504 Gateway Time-out on litellm.herrington.services — 2026-09-14

## Summary

All three 504s were generated by the **NGINX Ingress Controller** (nginx/1.31.1,
helm chart `nginx-ingress` v5.4.3 in namespace `ingress-nginx`) in front of
litellm. The root cause is the ingress controller's default
**`proxy_read_timeout 60s`**, which fires **before** LiteLLM's own 600s
per-deployment timeout because LiteLLM had not yet returned a response header.

This is **not** a LiteLLM failure. LiteLLM was still working the request; nginx
gave up and returned its own 504 error page after 60s of no response header.
Every retried request then succeeded — consistent with the "all stages finished
succeeded" behavior in the fabric data.

## Evidence

### All three 504s (nginx error log, pod `nginx-ingress-controller-4hvfj`)

Same client `10.10.0.32` (the fabric host), same upstream pod `10.244.4.98:4000`
(the current litellm pod `litellm-78879d446c-b2c82`). Timestamps below are the
pod's local time (CDT); UTC in parentheses.

1. `2026/09/13 23:24:18 CDT (04:24:18 UTC)` — `improve [improve@1]`, litellm:glm-5.3
   ```
   *147030 upstream timed out (110: Connection timed out) while reading response header from upstream,
   client: 10.10.0.32, server: litellm.herrington.services,
   request: "POST /v1/chat/completions HTTP/1.1",
   upstream: "http://10.244.4.98:4000/v1/chat/completions"
   ```

2. `2026/09/13 23:27:33 CDT (04:27:33 UTC)` — `coder [coder@1]`, litellm:coders
   ```
   *147055 upstream timed out (110: Connection timed out) while reading response header from upstream,
   ... upstream: "http://10.244.4.98:4000/v1/chat/completions"
   ```

3. `2026/09/14 09:52:32 CDT (14:52:32 UTC)` — `coder [coder@2]`, litellm:coders
   ```
   *151249 upstream timed out (110: Connection timed out) while reading response header from upstream,
   ... upstream: "http://10.244.4.98:4000/v1/chat/completions"
   ```

All three are `upstream timed out ... while reading response header` — the
exact signature of nginx `proxy_read_timeout` firing because the upstream sent
no data (not even a header ) within the window. No LiteLLM "timeout" surfaced
because 60s << LiteLLM's 600s deployment timeout.

### Generated nginx config for the litellm vhost

`/etc/nginx/conf.d/litellm-litellm.conf` (same on all 6 daemonset pods):

```nginx
location / {
    proxy_http_version 1.1;
    proxy_connect_timeout 60s;
    proxy_read_timeout 60s;    # <-- binding constraint
    proxy_send_timeout 60s;
    ...
    proxy_pass http://litellm-litellm-...-4000;
}
```

No timeout override exists on the Ingress (`kubectl get ingress litellm -n litellm -o jsonpath='{.metadata.annotations}'`
contains no `nginx.org/proxy-*timeout`). So the ingress controller's
**60s default** applies. Other vhosts in the cluster set higher values
(180s/600s/3600s) via annotations; litellm does not.

### Timing sanity check

- `proxy_read_timeout` is the timeout **between successive read operations** —
  nginx aborts if it receives nothing from the upstream for 60s.
- The fabric "elapsed into stage" numbers (124.7s / 193.2s / 203.7s) are
  **stage-wide**, and each stage issues many sequential LLM calls. The single
  call that died is the one that sat >60s with no response header — i.e. it is
  *inside* that window, validating the "60s read timeout fired on the last long
  request" hypothesis.

## Why "coders" (local deepseek) dominates 2/3

The 504s are first-token latency, not total throughput. For the **local
deepseek** deployment (`coders`), first-token can exceed 60s under queueing or
load (2 of 3 are coders; the third is a long glm-5.3 generation). That exceeds
the 60s read timeout while LiteLLM still has 600s on the clock, so nginx 504s
long before LiteLLM would.

## Separate failure mode: connection refused (handover)

Alongside the 504s, during the same morning on the same vhost, nginx logged
repeated `connect() failed (111: Connection refused)` to **stale litellm upstream
IPs** in the `10.244.3.x` range (e.g. `10.244.3.64`, `10.244.3.166`,
`10.244.3.193`, `10.244.3.240`) between ~09:26 and ~09:47 CDT (14:26–14:47 UTC):

```
*151040 connect() failed (111: Connection refused) while connecting to upstream,
  ... request: "POST /v1/chat/completions HTTP/1.1",
  upstream: "http://10.244.3.64:4000/v1/chat/completions"
```

This maps to the fabric `kind: network` — "error sending request for url …"
events. These old `10.244.3.x` endpoints (litellm used to run on node `alex`
before the current pod was recreated to `peaches`/`10.244.4.98` ~9d prior) were
still present in the controller's cached upstream zone; routing to a dead one
yielded connection refused → client-visible transport error → fabric failed over
to long-context → kimi-k3. All 6 controller pods now hold only the single
healthy endpoint `10.244.4.98:4000`, so this has self-healed. Note the daemonset
uses `max_fails=1 fail_timeout=10s`, so a single dead endpoint can flap a
reload-cycle worth of requests.

## Recommendations

1. **Align the proxy read/send timeout with LiteLLM's, on this vhost only.** The
   cleanest fix is ingress annotations (NGINX Ingress Controller reads them):
   ```yaml
   nginx.org/proxy-read-timeout: "600"
   nginx.org/proxy-send-timeout: "600"
   ```
   This raises nginx from 60s to match LiteLLM's 600s per-deployment timeout, so
   nginx stops being the binding constraint. Do not set it above LiteLLM's own
   timeout or LiteLLM would be the one returning its timeout instead.

2. Alternatively/additionally raise the controller **global default** in the
   `nginx-ingress` ConfigMap (e.g. `proxy-read-timeout: 600s`), but that affects
   every vhost — the per-Ingress annotation is safer and already the pattern used
   by the other 600s vhosts in this cluster.

3. **Tune the local deepseek (`coders`) deployment for first-token latency.**
   2 of 3 504s are coders. If first-token routinely approaches/exceeds 60s under
   load, consider: request queueing limits, warm/idle handling, batch size, load
   on the GPU node. First-token SLO for that model should be well under the proxy
   read timeout.

4. **Add `$upstream_response_time` / `$request_time` to the ingress access log**
   format. The current `main` format omits them, so correlating a 504 to the
   exact request/response timing currently requires the error log (which lacks
   request time-to-first-byte). Having these fields would make the next incident
   instantly diagnosable from the access log alone.

5. **Clean/reload upstream zones promptly when the backed pod is recreated.**
   The stale `10.244.3.x` endpoints caused the connection-refused burst. **This is
   already mitigated — verified, no config change required:**
   - The NGINX IC (OSS) reloads nginx automatically whenever the Service
     Endpoints change; all 6 daemonset pods converge on the healthy endpoint
     (currently all hold only `10.244.4.98:4000`).
   - litellm already has a **readinessProbe** (`/health/readiness`, period 10s,
     failureThreshold 3, timeout 5s), so Kubernetes removes a not-ready pod from
     Endpoints promptly and nginx stops routing to it.
   - nginx's built-in `proxy_next_upstream` default is `error timeout`, and the
     generated upstream uses `max_fails=1 fail_timeout=10s` — a failed/dead
     endpoint is failed over and marked down quickly.
   - Note: the F5 NGINX IC ConfigMap has **no `proxy-next-upstream` main key**, so
     per-vhost failover hardening beyond the above isn't available in OSS.
   The 09:26–09:47 connection-refused burst was a transient zero-ready/stale-endpoint
   window during a litellm pod recreate+node move; it self-healed and is not
   expected to recur while the readinessProbe stays configured.

## Implemented fixes (2026-09-14)

- **Finding 1 — applied.** Added per-Ingress annotations to the litellm Ingress so
  nginx waits up to 600s (matching LiteLLM) instead of 60s:
  `nginx.org/proxy-read-timeout: "600"` and `nginx.org/proxy-send-timeout: "600"`
  (`nauvoo-v2/manifests/apps/litellm/values.yaml`). This is the binding-constraint
  fix for the 504s.
- **Finding 3 — applied.** Added a `log-format` entry to the NGINX IC ConfigMap
  (`nauvoo-v2/manifests/infra/nginx-ingress/kustomization.yaml`) extending the
  default `main` format with `rt=$request_time urt=$upstream_response_time
  ua=$upstream_addr`, so future timeouts are correlatable from the access log
  alone. Also hoisted the previously out-of-band `client-max-body-size: 20m` and
  `error-log-level: debug` entries into declared gitops state (the live ConfigMap
  was OutOfSync; this reconciles it and preserves debug logging).
- **Finding 4 — verified, no code/config change needed** (see above): correct
  readinessProbe already present, controller auto-reloads, default failover
  active.
- **Finding 2 — intentionally not changed.** First-token latency for `coders`
  (local deepseek) depends on the inference hosts; can't be tuned here and is not
  a 504 cause once the nginx timeout is raised to 600s.
